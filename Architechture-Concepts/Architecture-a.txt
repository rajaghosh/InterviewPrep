This video explains how large platforms like Google and Amazon quickly check if a username 
is already taken. It focuses on the data structures and system design used to ensure this process 
is fast and scalable.

Key Data Structures
    * Redis Hashmap: An in-memory data structure used for caching to quickly check if a username 
    exists without querying the main database.
    * Tries (Prefix Trees): A tree-like structure that organizes strings by shared prefixes, 
    allowing for fast lookups and supporting autocomplete suggestions.
    * B+ Trees: Used in databases to index fields and keep keys sorted, which is ideal for 
    efficient lookups and range queries.
    * Bloom Filters: A probabilistic, memory-efficient data structure that provides a very fast, 
    initial check to see if a username "definitely not in the set," helping to avoid unnecessary database lookups.

The Real-World Process
The video explains that large-scale systems combine these data structures in a strategic flow:
    * Load Balancing: A user's request is first routed to the nearest regional data center.
    * Bloom Filter Check: The request hits a Bloom filter, which quickly checks if the username 
    is unavailable, preventing most requests from going to the database.
    * In-Memory Cache: If the Bloom filter is unsure, the request goes to an in-memory cache 
    like Redis, which can return an answer in microseconds if the username was checked recently.
    * Distributed Database: If there is a cache miss, the system performs an authoritative check 
    by querying a distributed database, such as Apache Cassandra or Amazon DynamoDB.

Seven popular design pattern

This video provides a summary of seven software design patterns, categorized into 
three types: creational, structural, and behavioral. 
These patterns offer reusable solutions to common programming problems.

Creational Patterns
    Creational patterns are focused on object creation.
    
    Singleton Pattern: Ensures that a class has only one instance and provides a single point 
    of access to it. An example is a logging system that uses a single logger for all activities.
    
    Builder Pattern: Used to construct complex objects step-by-step. This is useful when a 
    constructor would otherwise have many optional parameters, allowing for cleaner code and 
    method chaining.

    Factory Pattern: Creates objects without specifying the exact class that will be created. 
    It centralizes object creation logic into a single factory, which makes the code more 
    flexible and maintainable.

Structural Patterns
    Structural patterns deal with how objects relate to each other.

    Facade Pattern: Provides a simplified interface to a complex system of classes. It hides 
    the underlying complexity behind a single, clean interface, like a "buy now" button that 
    initiates multiple complex processes.

    Adapter Pattern: Allows objects with incompatible interfaces to work together. It acts 
    as a translator, similar to a physical adapter that lets a laptop plug into a different 
    type of port.

Behavioral Patterns
    Behavioral patterns handle communication and interaction between objects.

    Strategy Pattern: Allows an algorithm's behavior to be selected at runtime. It defines
     a family of interchangeable algorithms, such as different strategies for getting to 
     work (driving, biking, or taking the bus).

    Observer Pattern: Defines a one-to-many dependency between objects. When one object 
    (the subject) changes state, all of its dependents (the observers) are automatically 
    notified and updated. A YouTube subscription system is a good example of this pattern.

This video provides an overview of various authentication methods used in modern applications, 
starting with a basic definition and moving into more advanced concepts.

Authentication vs. Authorization
Authentication is the process of verifying a user's identity to ensure they are legitimate. 
Authorization, which follows authentication, is the process of determining what actions that 
user is permitted to perform.

    Basic Authentication
    This is the simplest form of authentication, where a username and password are sent with 
    each request as a base64-encoded string. This method is considered insecure on its own 
    because the encoding is easily reversible and is rarely used today unless secured with HTTPS.

    Bearer Tokens
    Bearer tokens are a more secure and common method where an access token is sent with each 
    request instead of a username and password. This is the current standard for API design 
    because it is fast, stateless, and easier to scale.

    OAuth 2.0 with JWT Tokens
    OAuth 2.0 is a protocol that allows users to log in through a trusted third-party provider 
    like Google or GitHub. When a user authenticates, the provider sends a JSON Web Token (JWT) 
    to the application. JWTs are stateless and contain user information and an expiration date.

    Access and Refresh Tokens
    For enhanced security, modern systems often use a combination of short-lived access tokens 
    and long-lived refresh tokens. An access token is used for making API calls, while a refresh 
    token is used to obtain a new access token once the current one expires, allowing the user 
    to remain logged in without re-authenticating. Refresh tokens should be stored securely on 
    the server side.

    Single Sign-On (SSO)
    SSO allows a user to log in once and gain access to multiple services, such as when you log 
    in to Google and are automatically granted access to Gmail, Drive, and Calendar. SSO typically 
    uses protocols like SAML or OAuth 2.0 to securely exchange user login information between 
    applications.

This video provides an in-depth explanation of seven key system design concepts for building 
reliable and scalable distributed systems.

1. The CAP Theorem
The CAP theorem states that a distributed system can only provide two of the three following 
guarantees at the same time: consistency, availability, and partition tolerance. 
    Consistency - All nodes see the same data at the same time.
    Availability - Every request to a non-failing node receives a response.
    Partition Tolerence - The system continues to operate despite network failures.

Because network partitions are unavoidable, systems must choose between consistency and availability. 
For example, Google Spanner prioritizes consistency, while Amazon's DynamoDB prioritizes 
availability by using eventual consistency.

2. Eventual Consistency
Eventual consistency ensures that if no new updates are made, all replicas of the data will 
eventually become the same. This approach is beneficial for large-scale systems because it 
allows write operations to complete immediately without waiting for all replicas to be updated, 
which improves performance and availability. The video mentions various conflict-resolution 
strategies, such as "last write wins" and using conflict-free replicated data types (CRDTs).

3. Load Balancing
Load balancers distribute incoming requests across multiple servers to ensure high availability 
and prevent a single server from being overwhelmed. The video differentiates between two main types:
    Layer 4 Load Balancers: Operate at the transport layer, making routing decisions based on 
    IP addresses and ports.
    Layer 7 Load Balancers: Operate at the application layer, enabling smarter routing decisions 
    by examining HTTP headers and request content.

4. Consistent Hashing
Consistent hashing is a technique used in horizontally scaled systems to solve the problem of 
adding or removing nodes without having to remap a large amount of data. By placing both keys 
and nodes on a circular hash ring, this method ensures that only a small fraction of data needs 
to be redistributed when a node is added or removed.

5. Circuit Breakers
The circuit breaker pattern is used to prevent cascading failures in a distributed system. 
A circuit breaker monitors the failure rate of a dependent service and can switch between 
three states:
    Closed: Requests flow normally.
    Open: Requests are blocked immediately, returning a fast failure.
    Half-Open: A few test requests are allowed to check if the service has recovered before 
    returning to a closed state.

6. Rate Limiting
Rate limiting controls the number of requests a client can make within a specific time 
window to protect the system from overload. The video explains algorithms for rate limiting, 
including the Token Bucket and Leaky Bucket algorithms, which help to smooth out traffic spikes 
and maintain an average request rate.

7. Monitoring & Observability
The video emphasizes that effective monitoring provides visibility into a system's behavior. 
Modern observability focuses on four key signal types: metrics, logs, traces, and events. 
The video also highlights the importance of effective alerting to reduce noise and identify 
real problems.

The video "Design Patterns & Anti-Patterns for Microservices Databases" provides a comprehensive 
overview of different strategies for managing storage and databases in a microservices architecture.
The video uses diagrams created with an AI tool called Eraser AI to illustrate these concepts.

Anti-Pattern: Shared Database
This approach involves multiple microservices sharing a single database. This is considered an 
anti-pattern because it undermines the core benefits of microservices, such as modularity and 
independent scaling. It can also lead to technical issues like deadlocks and inconsistencies 
when different teams manage the same database.

Recommended Pattern: Separate Databases
A better approach is to give each microservice its own separate database. This allows for decoupling 
and independent scaling, meaning a problem in one service won't affect others.

Handling Distributed Transactions
When a transaction spans multiple services, it becomes a distributed transaction. The video discusses 
two patterns to handle this:

Two-Phase Commit (2PC): A coordinator service orchestrates a two-step process to ensure all 
participating services either commit or roll back a transaction together. However, this can be 
complex to manage with many microservices.

Saga Pattern: This is an event-driven pattern where a series of local transactions are chained 
together via a message broker. If a service in the chain fails, compensating transactions are used 
to roll back the changes.

Other Key Patterns
API Composition: A read-focused pattern where a parent service aggregates data by querying multiple 
child services and combining the results.

CQRS (Command Query Responsibility Segregation): This pattern separates the databases and 
responsibilities for reading data (queries) from those for writing data (commands). This allows for 
the independent scaling of read and write operations, which is efficient as reads often occur more 
frequently.

Event Sourcing: This pattern stores every change to an application's state as a sequence of immutable 
events in an event log. This provides a full history of all changes for auditing purposes and allows 
the current state to be reconstructed by replaying the events.

This video provides a detailed explanation of authorization, differentiating it from authentication and detailing the three main authorization models used in application and system security.

Authorization vs. Authentication
Authentication confirms a user's identity to allow them to log into a system [00:00].

Authorization determines what the authenticated user is permitted to do, such as which resources they can access or actions they can perform [00:07].

Three Main Authorization Models
The video describes three common models for managing permissions:

Role-Based Access Control (RBAC)

This is the most common model, where users are assigned roles (e.g., admin, editor, viewer), and each role has a predefined set of permissions [01:53].

RBAC is used in many everyday applications like GitHub and team management tools [03:51].

Attribute-Based Access Control (ABAC)

This is a more flexible model that defines access based on a combination of user attributes, resource attributes, and environmental conditions [04:08].

Access is granted only when specific conditions based on these attributes are met [04:16].

Access Control Lists (ACL)

With ACLs, each specific resource has its own permissions list [02:22].

This model offers high specificity but is harder to scale in systems with millions of users [06:12].

Google Drive is a real-world example of ACL, where permissions are managed for individual documents [06:29].

Enforcing Authorization Rules
The video also explains how systems enforce these authorization models:

OAuth 2.0: A protocol for delegated authorization that allows a third-party application to access a user's resources on another service without the user sharing their password [07:37].

Tokens (JWT): Systems often use a token, such as a JSON Web Token (JWT), which contains information like the user's ID, roles, and access scopes. This token is sent with every user request, allowing the server to validate it and apply the correct permissions logic [09:13].

This video provides a detailed explanation of the Backend for Frontend (BFF) architectural pattern, which is a solution for supporting multiple client types, such as desktop and mobile apps, with a single backend.

The Problem
The video highlights the challenge of a single backend serving different clients with varying data needs. A single, monolithic backend might send a large amount of unnecessary data to a mobile app, leading to poor performance and a bad user experience [05:48]. This issue is even more pronounced when integrating with devices like Alexa, which require data in a completely different format [09:04].

The BFF Solution
The BFF pattern solves this by creating a dedicated, intermediary layer between the core backend services and the clients [10:06]. Instead of clients directly calling the backend, they call a specific BFF tailored to their needs (e.g., a desktop BFF or a mobile BFF).

This BFF layer handles the presentation logic, filtering out unnecessary data and making multiple internal calls to backend services if required [11:14].

The core backend remains generic, providing all possible information, and the BFF is responsible for customizing the response for each client [14:05].

The pattern is also highly effective in a microservices environment. For example, a desktop BFF might aggregate data from product, seller, and review services, while a mobile BFF might fetch from product and seller services but also an augmented reality (AR) service, skipping the review service entirely to save space [14:56].

Advantages of the BFF Pattern
Isolated Interfaces: The pattern allows for multiple, isolated interfaces that do not interfere with each other [16:32].

Faster Client-Specific Tweaks: Changes for a specific client can be implemented and deployed more quickly [16:59].

Data Security: Sensitive information can be filtered out at the BFF layer before reaching the client [17:25].

Protocol Flexibility: Different BFFs can use different communication protocols without affecting the core backend [17:43].

Request Aggregation: The BFF can act as an aggregator, reducing the number of API calls a client has to make [20:42].

Disadvantages of the BFF Pattern
Increased Complexity: It adds more components to the infrastructure that need to be managed, monitored, and deployed [23:25].

Potential Code Duplication: Similar logic might be duplicated across different BFFs, requiring careful management [22:47].

Increased Latency: Adding an extra network hop can slightly increase latency, which may not be ideal for super low-latency applications [23:53].

When to Use BFF
The video recommends using the BFF pattern in two main scenarios:

When there are significant differences in the data required by different clients [24:40].

When clients require different communication formats or protocols [25:49].
