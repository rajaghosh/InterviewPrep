Interview Strategy (Non-Tech)
    Here are the details for each of the non-technical aspects of a mobile system design interview.

---------------------------------------------------------------------------------------------------------

Clarify Requirements
    - This is the most critical phase. Your goal is to gather enough information to design the right solution, 
    not just *a* solution.
    - Ask questions to reduce ambiguity:** Don't make assumptions. Ask about user-specifics, platform 
    constraints, and other details. For example, "Will users need to share this content?"
    - Determine scope:** Clearly define what you're designing. Is it just the mobile app's front-end? Or 
    does it include the API and back-end?
    - Define functional requirements:** These are the core features of the app. For example, "Users can log in," 
    or "Users can create and view a list of items."
    - Define non-functional requirements:** These are the qualities of the system.
        - Offline mode:** Will the app need to work without an internet connection? What data should be accessible?
        - Minimize traffic bandwidth:** How can you optimize data transfer to save user data plans? Consider things
        like image compression, delta updates, and caching.
        - Minimize battery consumption:** What are the key battery drains (GPS, network requests, etc.) 
        and how can they be managed?
        - Optimize scroll: FPS = 60:** How will you ensure the UI is smooth? This often involves optimizing 
        rendering and avoiding heavy work on the main thread.
        - Data consistency:** Is **strong consistency** (all users see the same data at the same time) or 
        **eventual consistency** (data will eventually become consistent) required? For a chat app, you need 
        strong consistency. For a social media feed, eventual consistency is often acceptable.
        - Address scale of the engineering team:** Mention that the design should be easy for a team to work with. 
        Clean architecture and a well-defined API help.
    - Define out of scope:** Explicitly state what you won't be covering to manage expectations and keep the conversation
    focused. For example, "For the sake of time, I won't be designing the full back-end, but I'll define the API contract."
    - Address scale:** Ask about the number of users. **Daily Active Users (DAU)** is a key metric. A small app for 1,000 
    users has different requirements than an app for 10 million DAU.
    - Address authentication:** Ask about the required login methods. Will it be a simple email/password, or will it 
    involve third-party logins (e.g., "Sign in with Apple")?
    - Address target OS versions:** Ask which versions of iOS and Android the app needs to support. This affects which 
    frameworks and APIs you can use.
